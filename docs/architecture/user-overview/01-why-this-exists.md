# 1. Why This Exists — Problem & Philosophy

> **Target Audience:** Users — CTOs, Team Leads, and Architects evaluating agentic-tdd.
> **Key Goal:** Explain the problems that motivated agentic-tdd and the design philosophy that governs every architectural decision, so users can judge whether the trade-offs fit their organisation.
> **Status:** Published (v0.1.0-Beta) — Page 1 of the User Overview. See [the User Overview index](../README.md).

---

## Executive Summary

`agentic-tdd` is an **8-pass agentic TDD pipeline** for enterprise software development. It stops asking an AI model to "write code" in one shot, and instead **orchestrates AI to build software** as a deterministic, assembly-line process: Design → Contracts → Tests → Implementation → Refactor → Observability → Security → Documentation, each pass run by a specialised, scope-locked sub-agent and each producing an **atomic git commit**.

The core belief: **code generated by genAI is not yet production-grade.** Left unsupervised, AI-generated code accumulates small errors into large ones, drifts away from the architecture, and becomes spagehttified in a matter of days. `agentic-tdd` is an attempt to **engineer away that non-determinism** by the cumulative effect of multiple, incremental reliability steps — formal specs, deterministic verification, frequent drift correction, and human checkpoints — rather than hoping models get better. We hope to do a formal study of relaibility of agentic-tdd but anecdotally (from our daily usage) we find siginificant gains in accuracy, adherence to architecture and lower token usage.

## 1. The Problem

### 1.1 Context Bloat

Dumping entire codebases into a single agent window burns millions of tokens and causes "lost in the middle" attention drift: the model literally forgets constraints it was given at the top of a long prompt. The result is high cost *and* low accuracy.

### 1.2 Spaghetti Edits (Attention Degradation)

Asking one model to simultaneously write core logic, enforce security, handle error paths, and format logging produces **attention degradation** — the model will "lazy code" at least one constraint. A generalist agent trying to secure and implement at the same time performs measurably worse than a security specialist reviewing a pre-written file.

### 1.3 Architecture Drift and Specification Drift

Even with a good AGENTS.md file, the agent can generate code that is inconsistent with the existing architecture and patterns. In traditional development the docs lag the code; in agentic coding the *architecture itself* silently diverges unless the pipeline enforces a sync. genAI can write duplicate functionality, ignore existing libraries, introduce competing libraries and overall drift away from existing architecture and patterns.

### 1.4 'Agentic' vs. 'SKILLS'

Teams adopt the latest agentic tool without an engineering harness around it. There are many celebrated `AGENTS.md` files and agent "Skills" packs, but they govern the **agents**, not the **engineering around the agents** — context construction, verification gates, rollback, budget, and observability. This unstructured approach fails at enterprise scale.

**Why the pipeline beats "Skills" alone:** a *Skill* is a bundle of instructions an agent can load on demand — it makes the agent more competent, but it does not make the output verifiable. It has no test gate, no scope lock, no rollback, and no feedback loop. `agentic-tdd` treats capabilities as only half the problem: the other half is a **closed-loop process** (see [§ 2.1](#21-deterministic-verification-of-non-deterministic-generation) and [§ 2.5](#25-xstate-a-closed-loop-deterministic-orchestration-core)). A Skill improves what the agent *does*; the pipeline governs what the agent *may ship*.

### 1.5 The Underlying Problem: raw genAI code Is Not Production-Grade even with harnesses like opencode and claude-code.

It is not an exaggeration to say it is dangerous to let genAI loose on your code. Public, well-documented failure modes include hallucinated APIs, duplicate utilities, overwritten business logic, and unverifiable "it works on my machine" claims. These are not bugs to be waited out; they are the default behaviour to be engineered around.

## 2. The Design Philosophy

The philosophy is deliberately built from **classic, time-tested reliability engineering and Computer Science concepts** — not from hype. Seven principles follow.

### 2.1 Deterministic Verification of Non-Deterministic Generation

There is no single magic bullet for deterministic output. Small errors accumulate along a chain to produce large errors — the engineering answer is to **negate drift after every pass** i.e.,"fixing" errors before the next pass begins.

The two-pronged approach:

1. **Formal specs in purpose built specs formats** via Gherkin and diagrams. (Others like OWL, alloy, UML coming in the future.)
   - Gherkin (Given/When/Then) is strictly better than plain-English requirements for machine-readability.
   - Diagrams convey intent and boundaries far more efficiently than prose.
   - Mermaid was chosen **purely for Markdown compatibility**; future versions may adopt PlantUML for more expressiveness.
2. **Deterministic verification** — Test Driven Development (TDD) where we run formal tests after every genAI/agentic pass and run genAI in a loop till the tests pass. This ensures 'zeroing' the erros.

**TDD is the key philosophical pillar**: a deterministic test suite verifies an agent's non-deterministic generation. Tests are:

- **Deterministic** — they eliminate drift after every pass by encoding expected behaviour as executable constraints.
- **Token-free** — verification leverages effectively-free local compute; we do **not** use genAI to verify genAI, which removes both ambiguity and cost.

The pipeline therefore mandates **formal specs paired with frequent, iterative, exhaustive tests** (SDD/BDD + TDD), rather than choosing between them.

### 2.2 Artifact-Driven Development

In an AI-native pipeline, **the artifacts are the source of truth and the code is a byproduct.** Two artifacts drive everything:

- `.mmd` (Mermaid diagrams) — the architectural constraint.
- `.gherkin` (BDD specs) — the executable requirements.

**The artifacts are grounded in the real codebase first:** before the design agent drafts any `.gherkin` or `.mmd`, it consults the codebase knowledge graph (`codebase-memory-mcp`) — verifying the index is current and re-indexing if needed — so the design reflects existing symbols, conventions, and call chains rather than hallucinated structure. The index is the floor beneath the artifacts; the artifacts are the contract above them.

No agent is allowed to write core logic until a Mermaid diagram and a Gherkin specification have been generated, updated, **and approved by a human** ([ADR-0004 — HITL Gate after Pass 0](../adrs/0004-hitl-gate-after-pass-0.md)). Forcing the AI to map a state machine *first* enforces an architectural chain-of-thought, and the diagram becomes the strict mathematical constraint the code must satisfy.

> **The Digital Twin:** treating diagrams and specs as version-controlled, executable code creates a *digital twin* of the software. `@see` links let a developer trace any AI-generated method back to the exact state transition that dictated it — dramatically reducing the drift between what the agent builds and what was designed.

### 2.3 Minimising Specification Drift

Architectural diagrams and Gherkin specs are version-controlled, executable code. The pipeline enforces a mandatory **artifact sync rule**: agents MUST update `.mmd`/`.gherkin` and gain human approval before touching core logic, and the final Documentation pass re-checks specs against the finished code.

> [!NOTE] Where we hit the limits:
> While we started working on true spec parity, we soon realised that the complexity was delaying the rest of this framework. We do **not** claim true spec parity — fully synchronising diagrams, specs, and code is a hard open problem. What we deliver is *drift minimisation*: artifacts are committed and reviewed alongside code, so drift is caught early and cheaply instead of discovered months later. True parity is planned for future versions. We plan to have another agent to sync the specs with the code after the final pass. There is no timeline for this yet.

### 2.4 Reducing the Non-Determinism of genAI

Deterministic verification is necessary but not sufficient. `agentic-tdd` layers several guardrails and optimisations that each provide a non-trivial improvement and, *together* with unit tests, yield deterministic software output that:

- adheres to existing code conventions,
- does not over-write existing code,
- minimises blast radius / prevents unintended impact,
- uses existing functionality instead of duplicating it,
- does not hallucinate non-existent code.
- tight control on the scope of operation of each agent.

The mechanisms (each detailed on its own page):

| Mechanism | Page | Summary |
|---|---|---|
| Code indexing (`codebase-memory-mcp`) | [2. High-Level Architecture](02-high-level-architecture.md) | Semantic/AST index so agents get the right context and stop hallucinating existing APIs. |
| Controlled context building | [6. Context Engineering — Code Indexing & Token Savings](06-context-and-token-savings.md) | Index-first context + Context Compaction keep context accurate and minimal. |
| Agent guardrails | [5. Agent Prompt System & Routing](05-agent-prompt-system.md) | Scope-locked agents; file-glob permissions prevent Agent Trampling. |
| Multi-pass with self-correction | [3. The 8-Pass Pipeline](03-8-pass-pipeline.md) | Narrow per-pass scope; failing tests feed the error back for up to 3 retries. |

### 2.5 XState: A Closed-Loop, Deterministic Orchestration Core

The complexity of eight sequential passes, per-pass self-correction, and human gates is exactly where ad-hoc orchestration code decays into bugs. `agentic-tdd` models the whole pipeline as an **explicit XState state machine** — `createPipelineMachine` for the eight passes and `createSelfCorrectionMachine` for the per-pass retry loop ([src/core/machines/pipeline.machine.ts](../../../src/core/machines/pipeline.machine.ts), [src/core/machines/self-correction.machine.ts](../../../src/core/machines/self-correction.machine.ts); see [ADR-0002](../adrs/0002-xstate-machines.md)).

Why a state machine makes this tractable:

- **Explicit states, transitions, and guards** — the pipeline can never enter an undefined state. Every event (`PipelineStarted`, `HitlRequired`, pass success/failure) is a declared transition, so the control flow is inspectable and exhaustively testable instead of being implicit across scattered `if`/`while` loops.
- **Closed-loop verification** — the machine is the "loop" that closes the deterministic-verification principle (§ 2.1): after each pass it runs the test gate, and on failure it feeds the error log back into the Self-Correction Machine (up to 3 retries) before advancing. The model's non-deterministic output is always re-verified against deterministic tests before the next state is entered.


The result is a **closed loop**: human approves the design → agents produce → tests gate → failures bounce back → commits land atomically → the next pass starts from a clean, verified state.
This allows for easy and reliable and deterministic 'pause', 'resume' and 'abort' of the pipeline without fear of leaving the code in an inconsistent state.

### 2.6 Harness Independence

The harness is built **independent of any particular coding harness**. Agents are not embedded inside opencode; instead any CLI agent (ClaudeCode, agy, `pi`, etc.) can be integrated.

- No dependency on the direction of any single harness vendor.
- `pi` looks the most lightweight and is the probable default harness in future versions (planned).

> [!NOTE] Planned
> Harness-independence is a design principle; the default harness today is [opencode](https://opencode.ai) (see [ADR/index](../README.md)). Support for additional harnesses is future work — see the placeholder in [9. ADRs & Roadmap](../contributor-deep-dive/09-adrs-roadmap.md).

### 2.7 Build on Standard, Time-Tested Libraries

Rather than reinvent infrastructure, the project builds on mature, battle-tested components: TypeScript/Node.js, XState (state machines), Vitest (tests), execa (process execution), pino (logging), and `@ast-grep/napi` (AST parsing). This maximises robustness and minimises the "own-surface" the project must maintain.

## 3. The Solution at a Glance: AI as an Assembly Line

The philosophical principles are embodied in one pattern: **AI as an assembly line**. Instead of a single zero-shot prompt, development is broken into a strict sequential pipeline of eight specialised sub-agents:

```
Pass 0  Design & Architecture  →  design.mmd + spec.gherkin   [HITL gate]
Pass 1  Contracts & Types      →  type stubs in source files
Pass 2  TDD Test Generation    →  test file                   [Red phase]
Pass 3  Core Implementation    →  logic                       [Green phase]
Pass 4  Refactor & Optimise    →  complexity / DRY
Pass 5  Observability & Logs   →  error classes + logging
Pass 6  Security Hardening     →  OWASP + sanitisation
Pass 7  Documentation          →  docstrings + @see links + spec sync
```

Each pass's output is the **next pass's read-only context**, and each guarded pass runs the local test suite with self-correction before advancing. Every pass commits atomically, so rollback is a deterministic `git revert` of exactly one step ([ADR-0003 — Atomic Commits per Pass](../adrs/0003-atomic-commits-per-pass.md)).

## 4. What This Is (and Is Not)

| agentic-tdd **is** | agentic-tdd **is not** |
|---|---|
| An orchestrator / state machine that drives scoped sub-agents | A code indexer (that role is delegated to `codebase-memory-mcp`) |
| A TDD-enforcing pipeline with deterministic verification gates | A general-purpose autocomplete or pair-programming tool |
| A harness that *delegates* to a CLI agent | A replacement for a coding harness (opencode, etc.) |
| An artifact-first workflow (`.mmd`/`.gherkin` as source of truth) | A "generate-everything-in-one-prompt" tool |

> [!NOTE] Planned / Aspirational (do not assume available)
> Several enterprise features — LiteLLM SSO/budget gateways, Semgrep hard-fail gates, Bloop cross-repo indexing, and DevContainer sandboxing — are planned but not yet shipped. Where they exist in `infra/` or the roadmap, and where they are only planned, is flagged explicitly on the relevant pages. **Treat anything not explicitly implemented in `src/` or `infra/` as a placeholder.**

## 6. Is This For You?

`agentic-tdd` targets **enterprise teams** that already invest in tests and want a disciplined, auditable, per-commit agentic workflow — not solo experimenters looking for a chat-based code generator. It also **presupposes a test suite**: the pipeline's verification gates are meaningless without a runnable test command (`--test-cmd`).

### 6.1 Different Teams, Different Workflows

We recognise that users and organisations will diverge on the specifics of this harness:

- **Spec formats** — you may not want Gherkin/Mermaid at all, and may instead need your own internal specification standards.
- **Pass sequence** — you may want a different pass order, to drop certain passes, or to add your own.
- **Other customisations** — e.g. preferences around human-in-the-loop (HITL) gate placement.

### 6.2 Built for Nistapp, Adaptable by You

The current workflow, agent definitions, and prompts are **built for Nistapp internal use**. They are published as an **illustrative implementation** of one approach to getting deterministic output from genAI — a reference you can study, adapt, and apply to other domains and paradigms entirely your own. You are free to modify the harness for your own organisational workflow, including evolving it for frontend/backend/middleware nuances.

If you need help building a customised workflow, please contact Nistapp at **agentic-tdd-customisation@nistapp.com**.

### 6.3 Community & Project Status

This started as a **hobby project by one individual, without any corporate backing**. We do not yet have Discord, Reddit, or any other social media channels; until we set those up, please join the discussions on [GitHub Discussions](https://github.com/Nistapp/agentic-tdd/discussions).
